# Плагин `timetable` — страница записи на пары

**URL:** `my.centraluniversity.ru/learn/timetable`

Три функции: чипы со статусами в таблице расписания, ссылки на трансляции пар
(свои и других групп) и биржа обмена парами.

---

## API LMS, на котором всё держится

| Запрос                                                                | Что отдаёт                                                            |
| --------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `GET /api/student-hub/students/me`                                    | Профиль студента: `id`, `telegram`, `emails[]` (тип `Cu` — студпочта) |
| `GET /api/micro-lms/students/me/timetables`                           | Курсы студента и текущий слот каждой строки расписания                |
| `GET .../timetables/{courseId}/{eventType}/{eventRowNumber}`          | Все варианты слотов этой строки с массивом `conflicts`                |
| `POST .../timetables/{courseId}/{eventType}/{eventRowNumber}`         | Пересаживает студента (это делает сама LMS, расширение не вызывает)   |
| `GET /api/micro-lms/calendar-events/learn/courses/{id}/events/{дата}` | Фактические занятия курса за день — **только семинары**, лекций нет   |

Типы конфликтов в `conflicts[]`:

- `capacity` — мест нет, в интерфейсе чип «Нет мест»;
- `time` — пересечение с другой парой, чип «Пересечение с рядом пар».

Строка расписания однозначно задаётся тройкой `courseId` + `eventType`
(`lecture` / `seminar`) + `eventRowNumber`. Пересесть можно только внутри
одной строки — на этом построена вся логика обмена.

---

## `timetable_status.js`

Дописывает в колонку типа занятия чип с обобщённым статусом строки:
«Есть свободные», «Пересечения», «Нет мест» или «1 вариант».

**Как работает:** тянет расписание, для каждой строки запрашивает варианты
слотов и сводит их конфликты к одному статусу. `MutationObserver` следит за
перерисовкой таблицы Angular'ом и переставляет чипы заново.

## `timetable_join.js` — трансляции пар

Ссылку на пару в Контур.Толке студенты ищут в Яндекс Календаре или просят в
чатах. Сама LMS её не показывает, но она выводится из расписания: комната пары
— `https://centraluniversity.ktalk.ru/{calendarEventId без дефисов}`
(`calendarEventId` — id серии занятий). Название комнаты в Толке бывает
старым (аудиторию там не обновляют), поэтому аудитория — из LMS.

Включено всегда, тумблера нет. Под временем каждой строки:

- **«Ближайшая: …»** — когда следующее занятие («сегодня, 11:30–14:20»,
  «завтра, 10:00», «пт, 9 окт., 16:00»). Считается по дню недели, интервалу
  (раз в одну или две недели, фаза — от `startDate`) и границам семестра, в
  московском времени;
- **«Трансляция ↗»** — своя комната;
- **«Другие группы ▾»** — все варианты этой строки (другие преподаватели
  семинара, другие потоки лекции) из `timetables/{курс}/{тип}/{номер}`: кто
  ведёт, когда, где, ближайшее занятие и ссылка на трансляцию. Идущие сейчас
  — первыми и зелёным. Варианты грузятся по нажатию и кешируются на 30 минут;
  раскрытый список переживает перерисовку таблицы Angular.

Над таблицей — плашка **«Сейчас»** (пара идёт или начнётся в ближайшие 15
минут) и **«Дальше»** с кнопкой «Подключиться». Перерисовывается раз в минуту.

Сегодняшние **семинары** сверяются с занятиями дня: перенесённый помечается
«Сегодня в LMS её нет — проверь в чате курса» и в плашку не попадает. Лекции
не сверяются — LMS их в занятиях дня не отдаёт никогда, и любая сегодняшняя
лекция выглядела бы отменённой.

Курс строки ищется по названию в ячейке: сравниваются только буквы и цифры
(«Сердечки» меняют 🔴 на ❤️ прямо в тексте), а при своих названиях курсов
оригинал берётся через `cuLmsCourseNames.originalFor`.

Тест — `tests/timetable-join.test.ts` (подставная страница, часы заморожены).

## Биржа обмена парами

Три скрипта и один CSS. Бекенд — отдельный сервис
[lms-swap-backend](https://github.com/cu-3rd-party/lms-swap-backend).

Задача такая: слот подходит по времени, но забит. Записаться в LMS нельзя, пока
кто-то оттуда не уйдёт.

Биржа никого не пересаживает — она только сводит двоих, которым выгодно
поменяться, и показывает им контакты друг друга. Дальше как выйдет: если хотя
бы в одном из двух слотов есть свободное место, студенты пересаживаются сами,
по очереди. Если оба полные, через интерфейс не получится вовсе — ни один не
сдвинется первым, потому что чужое место занято, — и тогда местами их меняет
куратор, вручную.

### `swap_api.js`

Кладёт в `window.__culmsSwap` общий клиент: данные из LMS, ключ устройства,
запросы к бекенду. Ничего не рисует.

- `getIdentity()` — из `/students/me` берёт **только** `id`, студпочту и
  телеграм. Остальное (ИНН, СНИЛС, телефон, дата рождения) не читается и
  никуда не уходит.
- `getDeviceKey()` — случайный ключ в `browser.storage.local`. Токен сессии
  LMS лежит в HttpOnly-куках и скрипту недоступен, поэтому бекенд опознаёт
  студента по этому ключу.
- `isOrderable(option)` — слот годится для заказа, если у него есть конфликт
  `capacity` и **нет** `time`. Свободный слот заказывать незачем — на него
  можно записаться напрямую; слот с пересечением по времени бесполезен даже
  освободись там место.
- `request()` — все запросы идут через background (`SWAP_API`), а не напрямую:
  в Firefox content-скрипты не получают обход CORS из `host_permissions`.

### `swap_order_button.js`

Дописывает кнопку «Сделать заказ» в диалог выбора времени.

**Как работает:**

1. `MutationObserver` ловит появление `.events-list` в правом drawer'е.
2. Из подзаголовка диалога («Семинар 1 «Название курса»») достаёт тип пары,
   номер строки и название курса; курс сопоставляется с ответом
   `/timetables` — точным совпадением названия, а при неудаче без ведущего
   эмодзи.
3. Варианты из API сопоставляются с пунктами списка по индексу — порядок
   совпадает. Дополнительно сверяется день и время каждого пункта: связать
   заказ не с тем слотом хуже, чем не показать кнопку вовсе.
4. На подходящие пункты вешается строка с кнопкой. Клик по ней не всплывает
   — иначе LMS попыталась бы выбрать недоступный слот.

Если студент ещё не выбрал способ связи, кнопка не создаёт заказ, а
подсвечивает блок «Мои запросы»: совпадение без контакта бесполезно обеим
сторонам.

### `swap_menu.js`

Меню «Мои запросы» под таблицей расписания (вставляется после
`cu-student-timetable-events`).

- **Способ связи** — студпочта, телеграм из личного кабинета или своя строка.
  Значения подставляются из `/students/me`; недоступные варианты выключены.
  Пока студент не нажал «Сохранить», на сервер ничего не отправляется.
- **Список заказов** — курс, «отдаёшь → хочешь» и статус. Совпадения
  поднимаются наверх: только они требуют действий.
- **Совпадение** — контакт второй стороны и одна кнопка «ОК». Она убирает
  карточку только у того, кто нажал: вторая сторона своё совпадение ещё видит.
  Чем кончился разговор с куратором, сервису знать незачем, поэтому «обменялись»
  и «не получилось» не различаются.
- Список опрашивается раз в 20 секунд, пока страница открыта, и мгновенно
  обновляется по событиям `culms-swap-orders-changed` от кнопок в диалоге.

### `swap.css`

Цвета берутся из переменных Taiga UI, которые задаёт сама LMS
(`--tui-background-base`, `--tui-text-primary` и т. д.), поэтому блок
одинаково выглядит и в светлой теме, и в тёмной из плагина `dark-theme`.

## Что нужно вне плагина

- `manifest.config.js` → `host_permissions`: `https://lms.swap.cu3rd.ru/*`
- `manifest.config.js` → `web_accessible_resources`: все четыре файла биржи
- `src/background.ts` → обработчик `SWAP_API`: прокси с методами POST/PUT/DELETE
  и заголовками авторизации. Хост зашит в background константой
  `SWAP_BACKEND_ORIGIN`, а не приходит со страницы, — иначе скомпрометированный
  content-скрипт гонял бы через background запросы куда угодно.
